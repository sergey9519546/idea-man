# Task-fit challenge journeys

**Status: synthetic, unrun behavioral hypotheses.** These scripts are proposed
challenges, not customer quotes, observed failures, demand evidence, captured model
responses or successful tests. No candidate answers are included. Every row is
`not_evaluated` until an actual authorized local conversation and its resulting
state have been inspected. This document adds no cases to `cases.json` and is not
executable by the paired-output harness.

The target is useful task understanding: perform the requested operation with the
lightest adequate process, preserve constraints across turns, and verify the result.
Different defensible methods can pass. Method names, response length, confident
tone and a valid planner assessment do not establish semantic success.

## Challenge matrix

All facts and user turns below are supplied synthetic test inputs. `T1`, `T2`, etc.
are consecutive user turns; later turns are supplied only after recording the
preceding actual response. Do not invent an assistant turn to complete a script.
The contrast in each row changes the job, authority or evidence while retaining
part of the context.

## Use and evidence boundaries

- Start with a local dry review of the script and its supplied fixtures. Check that
  every required input is present and the task has a falsifiable pass condition;
  revise ambiguous test wording before drawing conclusions about the plugin.
- Do not execute new inference, install a runtime, send private plugin material to
  a service or relax the local-only constraint to run these journeys. If no
  authorized local inference is available, leave all semantic rows
  `not_evaluated`. Existing genuine local captures may be reviewed only where
  they contain the relevant task, turns and provenance; they cannot fill missing
  turns by implication.
- A future authorized run should retain exact supplied turns, source/fixture
  versions, plugin revision, available tools, budget, actual responses, tool
  actions, artifacts and failures. Mark missing evidence instead of silently
  rerunning or filling it in. Later user turns can change scope; they do not
  retroactively excuse an earlier violation.
- Separate **misinterpretation**, **overwork**, **underwork**, **incorrect or
  unsupported result**, and **delivery/recovery failure**. A single outcome can
  have more than one. Record the specific response excerpt, state difference or
  omission supporting each finding. Do not infer a failure from a preferred
  framework not being used.
- Local planner/receipt tests can check contracts, phase placement, blocking,
  invalidation and preserved scope. They cannot establish whether the host chose
  the right contract, performed sound reasoning, explained clearly or produced a
  useful idea. Manual actual-output inspection remains a separate gate.

This is a bounded challenge map. It does not establish customer frequency,
population coverage, model superiority, production safety, native installation or
release readiness. Urgent real-world situations must follow the host's safety
requirements; these synthetic desk exercises provide no reason to delay them for
an innovation workflow.

# Adaptive task recognition and workflow ordering

## Context assessment

Assess the active assignment, not just the last sentence:
1. Outcome: what must exist when done, in what count and format?
2. Intent: explore, vary, revise, review, select, develop, execute, resume or report.
   Several intents can coexist with dependencies.
3. Stage: blank page, brief, candidates, selected direction, approved artifact,
   production or verification. Determine from evidence, not elapsed time.
4. State: active objective, selected candidates, approved properties, rejected
   mechanisms and known reasons, authoritative source/version, unfinished commitments.
5. Constraints: audience, identity, style, budget, timing, tools, format and scope.
   Distinguish required constraints from flexible preferences.
6. Evidence: inspected artifacts, explicit user statements, hypotheses and unknowns.
   Internally link consequential routing decisions to a phrase or artifact.
7. Execution: available tools, existing authorization and what can actually be verified.

Keep an internal decision summary, not a chain-of-thought transcript. Assessments and
saved records contain conclusions, evidence and next steps, not hidden reasoning.

## Precedence and continuity

- Explicit edits and approved selections outrank broad ideation defaults.
- Review alone is read-only. "Review and improve" authorizes both.
- Requested counts override shortlist defaults. Explorations need honest labels, not
  invented passing scores or silent removal of requested options.
- A new constraint updates the active assignment; invalidate only affected work.
- "Try again" means diagnose the previous miss while preserving explicit approvals.
  "No" is a verdict, not a reason; your explanation remains a hypothesis.
- "Ultrathink", "think big" and "godmode" change depth, not the user's scope, tool
  permissions or source identity. They do not force a room for an exact edit.
- Approval of A and B preserves both. Do not choose one silently or ask again.
- Answer an interrupting status/side question briefly, then continue authorized work.
  Only clear cancellation or an incompatible objective replaces the task.

## Workflow composition

| Situation | Ordered work | Avoid |
|---|---|---|
| Fresh brief | Inspect → establish outcome/evidence → choose the needed diagnosis, research, invention or execution route → deliver/check | Mandatory insight or ideation on every topic |
| Six variants of A | Inspect A → lock invariants → variation matrix → generate → compare → deliver | Cosmetic duplicates |
| Remove one detail | Inspect exact source → edit → verify → deliver | Rebranding or reopening decisions |
| Choose and develop | Inspect → compare → delegated selection → develop → verify | Unnecessary permission pauses |
| Develop selected A | Inspect A → develop → verify → deliver | New alternatives to A |
| Review only | Inspect → criteria/evidence → critique → report | Silent modifications |
| Make approved work | Inspect → execution specification → produce → verify → deliver | Stopping at a prompt |
| Repeated rejection | Diagnose mismatch → change relevant mechanism → retry → verify | Repeating the same attempt |
| Resume | Load record → verify sources/state → continue outstanding work | Treat historical status as current |
| Approve and continue | Keep approval in context → next requested stage | Re-asking approval |

Dependencies are obligations, not a ritual. Skip a stage only when its output exists,
has been inspected, and still fits the current inputs. Each planned step needs an output
and acceptance condition. Tool success alone is not quality verification.

## Uncertainty and branching

Routing confidence is an internal judgment, not a calibrated probability. Missing source
material for an exact edit is a hard dependency; an inexpensive preference experiment is
not. Ask one targeted question if a wrong guess would materially waste the work. Continue
independent branches. Otherwise state a reasonable assumption and act.

Never fabricate a selection the user has not delegated. A request to "develop the best"
delegates selection; "help me choose" asks for a recommendation, not an unapproved commitment.

For complex jobs use ../scripts/studio.py plan with router-schema-v2.md and a schema_version: 2 assessment.
router-schema.md is version-1 compatibility only; use it solely for explicitly requested legacy assessments. The structured
planner gives dependency IDs, ready/blocked/done states and completion requirements.
It is advisory: the user and host rules govern actual execution. A mentioned workflow
does not create capabilities. If a tool is unavailable, deliver a usable fallback and
identify the requested execution still pending.

## Invalidation and replan checkpoints

Replan on changed objective, source failure, violated constraint, disproven premise or
missing capability. Preserve valid earlier work:
- Goal/audience: revisit brief, insight, candidates and downstream work.
- Constraints: revisit compliance from generation onward; retain useful research.
- Selection: retain research/brief, revisit development/execution.
- Feedback: preserve explicit approvals; invalidate the rejected branch.
- Tools: revisit execution/verification without discarding the creative goal.

After two similar misses, state the likely mismatch as a hypothesis and make a
structurally different attempt. Ask only if there is a decisive ambiguity.

## Completion evidence

Deliver the requested result plus only useful rationale and material limits. Distinguish
concept, specification, generated, inspected, tested and externally published results.
Saved local state is not global memory. Creative scores are opinions, not market evidence.
Do not promise autonomous future activity.

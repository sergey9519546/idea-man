# Selective artifact rubrics

An artifact can be an analysis, recommendation, experiment protocol or operating process as well as writing, media or code. Check the user's explicit acceptance conditions first. Use only relevant rows and record locations/evidence. Add domain-specific checks when the brief requires them; these are working criteria, not complete certification systems.

| Rubric ID / artifact | Core checks | Evidence needed | Avoid |
|---|---|---|---|
| `analysis` / diagnosis, causal analysis, research synthesis | Correct question/boundary; observations distinguished from hypotheses; alternative explanations; source support; valid units/denominators/calculations; uncertainty proportional to evidence; useful conclusion | Actual analysis and inspected source passages/data; reproducible calculation where material | Declaring root cause from correlation, fabricated measurements, analysis of the wrong system, hiding contradictory evidence |
| `decision` / strategy, choice, recommendation | Actual decision and authority; hard constraints; criteria tied to user goals; feasible alternatives; explicit tradeoff; uncertainty/sensitivity; revisiting trigger | Compared options and their evidence, constraints, assumptions and applicable calculations | Arbitrary weighted scores presented as measurements; invented ROI/demand; making an unrequested commitment |
| `experiment` / validation or research protocol | Testable assumption; target population/system; intervention or stimulus; observation/measure; comparison/control where feasible; confounds; decision rule; executable steps and limits | Actual protocol plus available resources, prior evidence and any executed observations | Calling a plan a completed experiment; manufactured samples, significance or results; changing success criteria after seeing results without disclosure |
| `process` / service or operations redesign | Current versus proposed flow; bottleneck/mechanism; ownership; handoffs; exception paths; constraints; stakeholder burden; dependencies; reversible pilot and outcome measure | Process description or observed workflow; relevant measurements; proposed/implemented distinction | Optimizing a local step while worsening the whole system; hiding shifted costs/work; checking only the happy path |
| `factual_writing` / article or research brief | Audience question answered; claims supported as worded; date/population context; accurate quotations; coherent argument; user voice; complete requested format | Actual draft plus inspected sources or supplied-document passages | Invented experience, citation decoration, SEO rules on non-SEO requests |
| `story` / screenplay, treatment or narrative | Character desire and choice; causal progression; earned consequences; knowledge/timeline/world consistency; voice; promised emotional effect; requested length/form | Actual story plus authoritative canon and relevant prior scenes | Treating imagined events as false external facts; silently changing accepted causality |
| `visual` / design, brand or exact image edit | Source identity; silhouette; palette; proportions; typography; source fidelity; requested delta; legibility at intended size; appropriate accessibility checks | Delivered image/render and approved reference side by side; target-size preview | Scoring a prompt instead of pixels; changing protected features; importing Idea Man's identity into a customer's project |
| `product` / product or experience concept | Problem and audience evidence; coherent core behavior; assumptions; flows and edge cases; scope; testable requirements; feasible next test | Brief, design/spec/prototype, research evidence where available | Invented customer demand; pseudo-precise impact forecasts; calling a mockup a working product |
| `campaign` / campaign, names or messages | Audience tension; distinctive mechanism/message; channel fit; brand voice; claims; pronunciation/ambiguity where relevant; requested variation count | Actual copy/names plus brief; inspected external checks if requested | Treating a name search as legal clearance; promised conversion results |
| `presentation` / pitch, deck or handoff | Decision or ask; coherent narrative; source support; readable hierarchy; consistency; recipient can act without hidden context | Actual document/deck render when relevant; cited claims; handoff context | Mistaking an outline for an authored deck; fabricated traction; omitted dependencies or unresolved decisions |
| `code` / implementation or interactive prototype | Requested behavior; relevant executed tests; error states; accessibility; dependencies; source constraints; limitations of verification | Actual files and appropriate executed checks, plus rendering if needed | Claiming behavior from prose/screenshots; broad unrun test claims; calling a handoff implementation |
| `game` / game concept or prototype | Player verbs; core loop; understandable feedback; progression; constraints; playability when execution requested | Design artifact; actual playtest evidence for a working build | Confusing theoretical balance with observed playtesting |

## Method and task fit

Before judging polish, check that the result answers the requested operation. A list of solutions does not satisfy a root-cause diagnosis. A critique does not authorize rewriting. A persuasive story does not prove a business mechanism. A correct calculation may still answer the wrong question. Note when a chosen thinking method contributed no useful distinction or encouraged a scope violation; feed that observation into a routing correction rather than inventing a quality score.

## Shared checks

- Scope, requested count and format are fulfilled; approved decisions and hard constraints are preserved.
- Source and output versions match the actual inspected artifacts. Recheck dependent findings after a changed source or constraint; do not reuse a stale pass.
- Proposed mechanisms, assumptions, estimates, observed data and validated conclusions are labelled distinctly.
- Material counterevidence and uncertainty remain visible. Missing tools or evidence produce `not_checked`, not a passing criterion.
- Completion claims match the action performed. A prototype can be implemented but not behavior-tested; a concept can be ready for discussion but untested with users.

For a narrow edit, check the requested change and protected properties rather than running the entire table. For multiple deliverables, apply the relevant rubric to each and disclose the resulting coverage. A failed critical acceptance condition cannot be hidden by averaging unrelated passing checks.
